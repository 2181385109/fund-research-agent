# 压测基线与瓶颈定位（S12）

> 单机（Windows 11 笔记本 + WSL2 Docker）、mock LLM（场景 E 除外）、**闭环**负载下的**基线**，用来给 S13 的优化提供「优化前」的数字和证据；不是容量规划，也不能外推到别的机器。
> 每个数字都带 n，并指向 `reports/perf/` 下的原始文件。方法与口径见 `loadtest/README.md` 和 ADR-050；限制见本文 §6 与 `docs/LIMITATIONS.md`「压测（S12）」。

## 0. 结论摘要

| 问题 | 结论 | 证据 |
|---|---|---|
| 系统最先撑不住的是哪里？ | **ai-service 里 CPU 上的交叉编码重排**。单次检索 3.56 s（1 并发），其中重排 3.52 s（98.9%）；一个检索就吃掉 6.5 个核（653%），2 并发整机 CPU 已 90%，吞吐封顶在 **0.34 QPS**（2 并发），再加并发只是排队（8 并发 P50 30.7 s） | §2.1 A；§4.1；`reports/perf/20261003T054246Z_A/` |
| 文档问答（B）全链路能撑多少？ | **≈ 0.24 QPS**（4–8 并发），1 并发 P50 7.9 s（LLM 3.9 s + 工具 4.0 s，工具里几乎全是检索）；8 并发 P50 32.0 s / P95 58.2 s | §2.2；`reports/perf/20261003T061237Z_B/` |
| 有没有崩溃点？ | **有：16 并发检索会把 ai-service 内存顶爆被 OOM 杀死**（容器上限 2560 MiB，8 并发时峰值就已经 2560 MiB）。B 的 16 并发三次运行全部失败（1 次部分成功后崩溃，2 次因重启后冷启动再次被杀）；只含检索的 A 探针 12 并发正常、16 并发 7606 / 7606 个请求失败 | §4.2；`reports/perf/evidence/ai_service_oom_during_B16.txt` |
| 数据库 / 工具类问答（C）呢？ | 不吃检索，**随并发近线性扩展**：64 并发 9.97 QPS、P50 5.8 s、0 错误；延迟几乎全是（回放的）LLM 时间。128 并发被 backend 的**准入上限（同时 64 路对话流）**直接 503 拒绝（98% 为 HTTP 503，且此时压测端 Locust 的 CPU 已 97%，这一档不算干净的测量） | §2.3；§4.4 |
| 语义缓存命中路径（D） | 1 并发 P50 **80 ms**（对比 B 未命中 7.9 s，同为 mock）；吞吐在 16 并发后封顶在 **≈ 43 QPS**；ai-service 用到 3 个核，py-spy 显示命中路径的 CPU 主要花在**查询向量化**（`embed_documents` 占 66% 样本） | §2.4；§4.5 |
| backend（Java）是不是瓶颈？ | **不是**：C 场景 64 并发时 backend 容器 CPU 14%；JFR（32 并发、90 s 窗口）JVM 用户态 CPU 均值 1.1%，没有占比超过 3.4% 的热点方法 | §4.3；`reports/perf/profiles/jfr_backend_C32/summary.md` |
| mock 可信吗？ | 按路线拆开比：E 里走文档检索路线的请求，1 并发 P50 8.58 s（B 的 1 并发 7.87 s，+9%），3 并发 11.34 s、5 并发 19.03 s，落在 B 相邻档之间；走 SQL / 工具路线的请求 1 并发 3.89 s（n = 6；C 的 1 并发 4.42 s，−12%）。mock 不会随并发变慢，真实 API 可能会；E 只测到 5 并发 | §2.5 |

**基线一句话**：当前版本在这台机器上，**有检索的问答（A / B / E）吞吐都不到 0.35 QPS，且 ≥ 16 并发会 OOM**；没有检索的问答能撑到 backend 的 64 路准入上限；缓存命中路径 43 QPS。S13 的优化应当先对着重排的 CPU 与内存，其次是命中路径的查询向量化（§5，仅是候选，没有做）。

## 4. 瓶颈定位

### 4.1 CPU：交叉编码重排（证据链）

1. **分段打点**（`/v1/retrieve` 的 `timings_ms`）：1 并发检索总耗时 3.56 s，其中重排 3.52 s（98.9%）；8 并发 29.26 s 里重排 28.94 s（§2.1）。B 里 `search_fund_documents` 占 1 并发服务端总耗时 7.43 s 的 3.93 s（53%）。
2. **docker stats**：1 个检索并发时 ai-service 容器 CPU 653%；`torch.get_num_threads()` = 8（容器内实测，宿主机 8 物理核）。由此推算每次检索约 3.5 s × 6.5 核 ≈ 23 核·秒；2 并发时 CPU 1307%、宿主机 90%，吞吐封顶（0.34 QPS × 23 核·秒 ≈ 7.8 核，与「8 个物理核跑满」吻合——这是由测得的中位数做的粗略推算，不是直接测量）。
3. **py-spy**（B 场景 4 并发，55 s 采样，`reports/perf/profiles/pyspy_B4/`；py-spy 与负载同时运行，样本数是近似值）：

   - 8558 个样本里，**73.4% 在 `score (fund_ai/rerank/cross_encoder.py:57)` ← `retrieve (fund_ai/retrieval/service.py:242)` 之下**，全部在 `AnyIO worker thread`（检索跑在线程池里）；
   - 栈顶（自身时间）：`torch/nn/modules/linear.py:134 forward` 51.6%、`sdpa_attention_forward` 6.9%、`activations.py` 3.7%、`layer_norm` 2.1%——都是 `xlm_roberta`（`bge-reranker-base`）的前向计算；py-spy 只看得到 Python 帧，C++ 算子表现为调用它们的 Python 函数；
   - 事件循环线程（`MainThread`）占 24.7%，栈顶是 `asyncio/runners.py:118`（应为等待，py-spy 把它算作活跃，没有深究）。
4. **连带效应**：重排占满 CPU 之后，ai-service 里其它事情都变慢：嵌入 0.01 → 0.24 s（A，1 → 8 并发）、`get_fund_db_schema` 29 → 382 ms（B，1 → 8 并发）。

完整的栈汇总表见 `reports/perf/profiles/pyspy_B4/summary.md`，火焰图见 `reports/perf/profiles/pyspy_B4/ai_flame.svg`（浏览器打开）。

### 4.2 内存：并发检索把 ai-service 顶爆

- **容器内存峰值**（`docker stats`，窗口内最大值，MiB；上限 2560）：A：2176（1 并发）/ 2344（2）/ 2435（4）/ **2560（8）**；B：1474 / 2236 / 2356 / **2560** / **2560**（16）。未加载检索模型时（C 场景，不走检索）128–237 MiB；加载后单并发检索 1.4–2.2 GiB。
- **OOM 杀死**：内核日志（`dmesg`）记录了 `Memory cgroup out of memory: Killed process … (uvicorn)`，被杀时 `anon-rss` 2.23–2.59 GB、`file-rss` 0.24–1.06 GB；本次开机以来共 10 条：4 条属于 A 的 16 并发探针（探针后 `RestartCount=4`），其余 6 条出现在探针之前、对应 B 的 16 并发期间的几次崩溃（dmesg 时间戳是开机后秒数，没有逐条对齐到墙钟）；`docker events` 在 B 的 16 并发 r2 / r3 交界处（14:51:00）也有 `oom` 事件（`reports/perf/evidence/ai_service_oom_during_B16.txt`）。杀死后 Docker 按 `restart: unless-stopped` 重启，backend 在这几十秒里收到 gRPC `UNAVAILABLE`，错误回给用户（`done.status=error`、`upstream_unavailable`）；重启后模型是**懒加载**的，如果此时 16 个并发请求同时涌入，会在冷启动期间再次被杀（B 的 r2、r3）。
- **门槛**：只含检索的 A 探针（没有 backend、没有 LLM）12 并发窗口内 13 个请求全部成功（但内存已经顶在 2560 MiB），16 并发 7606 个请求全部失败。**门槛在 12–16 个并发检索之间**；这个值取决于 `mem_limit`、基线内存和每个并发重排的激活内存，没有做更细的二分，也没有区分激活内存、glibc arena 或模型副本各占多少。
- 备注：这是**当前默认内存预算（PLAN §3 的 2560m）下的行为**，不是缺陷定论；提高 `mem_limit` 会把门槛推高，但在这台 10 GB 的 WSL 里余量很小。

### 4.3 backend（Java）不是瓶颈

- C 场景（没有检索拖累，对 backend 最苛刻）：容器 CPU 64 并发 14%、内存 552 MiB；对话流并发达到 64 才会触发准入拒绝（§4.4）。
- **JFR**（`profile` 设置，C 场景 32 并发，90 s 窗口，`reports/perf/profiles/jfr_backend_C32/summary.md`；录像 13.5 MB 不入库）：窗口内 178 个执行样本（≈ 2 个/秒，对比 10 ms 一次的采样上限 100 个/秒——线程大多在等待），栈顶方法最高占 3.4%（`HashMap.getNode`），**没有热点**；线程组：`grpc-chat` 49%、`http-nio-8081-exec` 37%；`jdk.CPULoad` 的 `jvmUser` 窗口内均值 1.11%。录像从 JVM 启动起共 189 s，启动和注册压测账号（BCrypt）的样本已用时间窗口排除（`stack_summary.py --from/--to`）。
- D 场景（命中路径，backend 要处理很多短请求）：backend CPU 41%，不是瓶颈。

### 4.4 backend 的准入上限（设计内的拐点）

`GrpcAiServiceClient` 的 `maxConcurrentChats`（默认 64）限制同时进行的对话流数，超出直接 HTTP 503（C 的 128 并发：窗口内 49 495 / 50 566 个 503，§2.3）。这是**有意的背压**，所以「没有检索的问答」的容量拐点是 64 路并发流（≈ 10 QPS，该比例由回放的 LLM 延迟决定：并发 / 平均对话时长 ≈ 64 / 6.4 s）。对有检索的问答，这个上限根本到不了——重排和内存先到顶。

### 4.5 语义缓存命中路径：查询向量化

D 场景 64 并发的 py-spy（`reports/perf/profiles/pyspy_D64/`，40 s；**与负载同时运行，吞吐被拖慢到 17.8 QPS**，只能看占比）：7949 个样本里 **66.2% 在 `embed_documents (fund_ai/embedding/bge.py:66)`**（`sentence_transformers.encode` → BERT 前向），在 uvloop 的线程池工作线程里；其中 `torch/nn/modules/module.py:1377 convert` 单项自身时间 13.7%、`compute_should_use_set_data` 2.9%——每次 `encode` 调用里的模块转换（疑似 `.to(device)`）占了明显比例，**这是观察，没有验证因果**。命中路径的吞吐封顶 43 QPS 时 ai-service 用了 ≈ 3 个核，与「查询向量化是 CPU 瓶颈」一致。

## 6. 局限（读数字前请看）

1. **闭环负载**：过载时排队延迟被低估（协调遗漏）；拐点按「QPS 不再上升」判定。没有做开环（固定到达率）测试。
2. **压测端与被测栈在同一台机器**：Locust 与 Docker 抢 CPU。`summary.json` 记录了宿主机与 Locust 进程的 CPU：A / B / C / E 里 Locust ≤ 12%（C 的 128 并发 97%、D 的 16–64 并发 27%）。D 的封顶值（43 QPS）有一部分可能受压测端和 backend 到客户端之间的开销限制（§2.4 的约 1 s 未归因）。
3. **WSL2 内存 10 GB、8 物理核**：结论（尤其是 OOM 的门槛和 CPU 封顶值）只对这台机器、这套内存预算成立。
4. **mock LLM 回放真实记录**：不会随并发变慢、延迟是回放（同一个问题每次相同）、`usage` 不是计费数字；工具执行是真的。E（真实 DeepSeek）只测了 ≤ 5 并发、246 个请求。
5. **A / B 低并发的窗口内完成数少**（A 的 1 并发 33 个、B 的 1 并发 13–14 个、E 的 1 并发 9–10 个），P95 / P99 只能参考；B 的 16 并发窗口比 P50 还短。
6. **docker stats 的粒度**：`--no-stream` 每 ~1.5 s 一次，CPU% 是内核 1 s 左右窗口的值；表里的是窗口内均值的三次中位数。
7. **py-spy**：只看得到 Python 帧；采样与负载同时运行会拖慢被测进程（py-spy 报告「落后 1–2 s」）；样本数是近似值，占比只作定位。JFR 没有采样内核 / 网络等待。
8. **没有测的**：HTTP 传输下的压测（S9 有预实验，`docs/perf/grpc_vs_http.md`）、限流与配额在压测下的行为（压测中关闭）、批量入库（S11）的吞吐、私有知识库检索、更大的数据量（只有 20 只基金、13 812 块）。
9. **复现**：见 `loadtest/README.md`。各运行的命令行原文在对应 `summary.json` 的 `command` 字段，战役脚本是 `loadtest/campaign.sh`；原始逐请求记录在 `runs/*/requests.jsonl.gz`，docker stats 采样在 `dockerstats.jsonl.gz`。
