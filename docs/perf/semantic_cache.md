# 语义缓存：阈值校准、误命中率与延迟（S10）

> 单机（Windows 11 + WSL2 Docker，ai-service 容器 / 宿主机本地进程）、单次运行集合的**预实验数字**，不是压测基线（压测是 S12）。
> 每个数字都带 n 或分母，并指向 `reports/` 下的原始文件。决策与取舍见 ADR-048，局限见 `docs/LIMITATIONS.md`「语义缓存与限流（S10）」。

## 0. 结论摘要

| 问题 | 结论 | 证据 |
|---|---|---|
| 只用向量相似度能不能选出可用的阈值？ | **不能**。dev 上难负例（只差一个关键要素）的余弦相似度中位数 0.819、最大 0.992，同义改写中位数 0.919，两个分布大面积重叠；**零误命中的阈值是 0.995，此时 recall = 0 / 72**（test 上同一阈值 0 / 92） | §2、`reports/cache_calibration/20261002T051202Z_dev/` |
| 怎么办 | 命中 = 相似度 ≥ 0.80 **且**两个问题的「关键要素签名」一致（基金、数字与时间、术语概念）。守卫是启发式，不是证明 | ADR-048、`fund_ai/cache/guard.py` |
| test 上（只跑了一次）的 recall / 误命中率 | recall **77 / 92 = 83.7%**（95% 区间 74.8%–89.9%）；难负例误命中 **3 / 132 = 2.3%**（0.8%–6.5%）；无关对误命中 0 / 40 | §3、`reports/cache_calibration/20261002T051218Z_test/` |
| 误命中长什么样 | 3 次全部来自词典里没有的区分维度：「股票」vs「港股通标的股票」× 2、「仓位变化」vs「市场展望」× 1 | §3 |
| 命中 vs 未命中的延迟（真实 DeepSeek，n = 10 个问题） | 首字 **56.8 ms vs 5409.7 ms**（中位数），总耗时 **58.1 ms vs 5776.4 ms**；命中不花 token（未命中 10 次共 126458 token） | §5、`reports/semantic_cache/20261002T052836Z/` |
| 缓存本身的开销（真实 BGE + 真实 Redis，n = 200） | 嵌入 8.4 ms（中位数）+ 向量检索 0.6 ms（库里 20 / 1000 条）～1.5 ms（10000 条）+ 守卫 0.04 ms | §4、`reports/semantic_cache/20261002T052808Z/micro.json` |

## 1. 校准集与规则

- 数据集 `eval/datasets/cache_pairs_v1.jsonl`（472 对，sha256 `ebca9f77…5a8f`）：同义改写对（应命中）、金融场景难负例对（只差一个关键要素，**不能**命中）、无关对（参考基线）；dev 208 对 / test 264 对，**按意图划分**（test 上的措辞和槽位都是选阈值时没见过的）。构造方式、来源和局限见 `eval/datasets/CACHE_PAIRS.md`——**模板措辞由执行者手写，不是真实用户的提问分布；没有人工审核标签**。
- **规则在看到任何结果之前写进了代码**（`ai-service/src/fund_ai/eval/cache_calibration.py` 文件头，红线 2）：规则 A（只用相似度）：dev 上难负例误命中数为 0 的最小阈值；规则 B（相似度 + 守卫）：不低于 0.80、dev 上难负例与无关对都零误命中的最小阈值。**规则 B 与守卫是在 dev 第一次扫描之后、实现守卫之前补充的**（文件头如实记录；dev 扫描发现纯相似度不可用是补充的原因）。守卫词典只依据 dev 调整。
- test 只跑一次：`TEST_RUN.json` 标记存在时脚本拒绝再跑。另报配置 B_dev（词典只保留 dev 问题里出现过的概念），用来估计守卫对「没见过的区分维度」的泛化。

## 2. dev 结果（选阈值用）

最终 dev 运行：`reports/cache_calibration/20261002T051202Z_dev/`（git `b5a3a59`，dirty=false）。同目录下更早的三次 dev 运行是实现过程中的迭代，**保留不删**：`…050213Z_dev`（只用相似度的第一次扫描，数据集当时还有「基金代码紧贴年份」的渲染缺陷，是它发现了纯相似度不可用）、`…050706Z_dev`（数据集修复、加了守卫，还没有 B_dev）、`…050956Z_dev`（加了 B_dev，代码还没提交）；后两次的阈值选择结果与最终一次相同。

难负例与同义改写的相似度分布（余弦，dev）：

| 类别 | n | 中位数 | 最大 |
|---|---|---|---|
| 难负例（全部） | 104 | 0.819 | **0.992** |
| 难负例：换基金 | 52 | 0.768 | 0.898 |
| 难负例：改一个槽位（费用种类、季度、份额类别、上下限…） | 44 | 0.893 | 0.987 |

| 同义改写 | 72 | 0.919 | 0.987 |
| 无关对 | 32 | 0.465 | 0.862 |

各阈值下的命中数（dev；A = 只用相似度，B = 相似度 + 守卫；完整网格见 `summary.json`）：

| 阈值 | A：同义命中 | A：难负例误命中 | A：无关误命中 | B：同义命中 | B：难负例误命中 | B：无关误命中 |
|---|---|---|---|---|---|---|
| 0.70 | 66 / 72 | 90 / 104 | 1 / 32 | 64 / 72 | 0 / 104 | 0 / 32 |
| **0.80** | 66 / 72 | 57 / 104 | 1 / 32 | **64 / 72** | **0 / 104** | **0 / 32** |
| 0.85 | 59 / 72 | 44 / 104 | 1 / 32 | 58 / 72 | 0 / 104 | 0 / 32 |
| 0.90 | 47 / 72 | 24 / 104 | 0 / 32 | 46 / 72 | 0 / 104 | 0 / 32 |
| 0.95 | 10 / 72 | 13 / 104 | 0 / 32 | 10 / 72 | 0 / 104 | 0 / 32 |

| **0.995（A 选出）** | **0 / 72** | 0 / 104 | 0 / 32 | 0 / 72 | 0 / 104 | 0 / 32 |

- 选出的阈值：A = **0.995**（recall 0 / 72），B = **0.80**（recall 64 / 72 = 0.889，难负例误命中 0 / 104）。

- 常见的经验阈值（0.90–0.95）只靠相似度时，dev 上难负例误命中 13–24 / 104。

## 3. test 结果（只跑一次）

`reports/cache_calibration/20261002T051218Z_test/`（git `b5a3a59`，dirty=false；阈值取自 dev 运行 `…051202Z_dev`，未在 test 上调整）。n：同义改写 92、难负例 132、无关对 40。

| 配置 | 阈值 | recall（同义命中） | 难负例误命中率 | 无关对误命中 |
|---|---|---|---|---|
| A 只用相似度 | 0.995 | 0 / 92 = 0.000（区间 0–0.040） | 0 / 132 = 0.000（0–0.028） | 0 / 40 |
| **B 相似度 + 守卫（线上默认）** | **0.80** | **77 / 92 = 0.837（0.748–0.899）** | **3 / 132 = 0.023（0.008–0.065）** | 0 / 40 |
| B_dev 守卫词典只含 dev 出现过的概念 | 0.80 | 77 / 92 = 0.837 | 3 / 132 = 0.023 | 0 / 40 |

（区间是 Wilson 95%。precision 对难负例：B = 77 / 80 = 0.963。）

**3 次误命中**（全部是守卫词典里没有的区分维度；相似度 0.825–0.917）：

| 子类型 | 问题 1 | 问题 2 | 相似度 |
|---|---|---|---|
| `slot:A`（股票 vs 港股通标的股票） | 华安科技动力混合的基金合同对港股通标的股票仓位的下限怎么规定？ | 根据基金合同，华安科技动力混合投资股票的比例下限是多少？ | 0.825 |
| `slot:A` | 汇添富中证芯片产业指数增强发起式合同规定股票占基金资产的比例下限是多少 | 根据基金合同，汇添富中证芯片产业指数增强发起式投资港股通标的股票的比例下限是多少？ | 0.917 |
| `slot:T`（仓位变化 vs 市场展望） | 2026年一季报里，中银创新医疗的基金经理对仓位变化怎么说？ | 2026年一季报里，中银创新医疗的基金经理对市场展望怎么说？ | 0.896 |

- **B_dev 与 B 完全相同**：说明这 3 次误命中不是因为「test 专用词条」才漏掉的，而是词典根本没有这类概念；也说明本次 test 上没有一个误命中是靠「我在写词典时知道 test 的设计」才避免的。
- 同义改写里被守卫否决的（相似度 ≥ 0.80 但签名不一致）有 11 / 92，另有 4 / 92 在相似度阈值上就没过。原因分析见 LIMITATIONS S10-4；因为是 test 上看到的缺陷，**没有改守卫**。
- 对照（**不用于重新选阈值**）：test 上 B 在 0.90 时 recall 58 / 92、难负例误命中 1 / 132，在 0.95 时 21 / 92 与 0 / 132。规则已经定了，阈值取 0.80。

**这 2.3% 是什么**：每个难负例都是「缓存里恰好已经有一个只差一个要素的近邻」，所以 2.3% 是**条件**误命中率。真实流量里这种近邻出现的概率远低于 100%，生产误命中率更低，但**没有测**（校准只量了一对问题的决策，生产里缓存取 top-3 逐个过守卫，候选多了机会也多）。因此缓存**默认关闭**，打开前请看这一节。

### 事后诊断（排除畸形问题对）

test 跑完之后发现数据集有渲染缺陷：「天弘中证医药100」遇到年份开头的槽位时被拼成「天弘中证医药100202 6年」（8 对：dev 1、test 7，见 `CACHE_PAIRS.md`）。**数据集和官方数字都没有改**；在同一次运行的逐对相似度上排除这 8 对重新计数（不重新嵌入，阈值与守卫不变），**事后诊断**：test：B recall 77 / 89 = 0.865、难负例误命中 3 / 128、无关 0 / 40；dev：B recall 64 / 72、难负例误命中 0 / 103。文件：各运行目录下的 `addendum_excluding_malformed.{json,md}`。

## 4. 缓存本身的开销（micro，不含 LLM）

`reports/semantic_cache/20261002T052808Z/micro.json`（宿主机 Windows 上的 Python 进程；真实 `BAAI/bge-small-zh-v1.5` CPU 推理 + 真实 Redis 8（compose 里的实例，`fra:semcache:*` 之外的键不碰，独立命名空间，结束时清理）；每项 n = 200，毫秒）：

| 阶段 | 中位数 | p95 | 说明 |
|---|---|---|---|
| 嵌入（一条问题） | 8.37 | 9.60 | 命中与未命中路径都要付 |
| 向量检索 top-3，库里 20 条 | 0.59 | 0.85 | Redis `FLAT` 索引 |
| 向量检索 top-3，库里 1000 条 | 0.60 | 0.83 | |
| 向量检索 top-3，库里 10000 条 | 1.46 | 1.83 | 线性增长，万级以上应换 HNSW |
| 关键要素守卫（一对问题） | 0.04 | 0.08 | 纯 CPU |
| 回放事件生成（300 个 token 事件 + 出处） | 0.04 | 0.05 | 不含网络写出 |

**未命中路径的额外开销** ≈ 嵌入 + 检索 ≈ 9–10 ms（e2e 里命中响应的 `cache_lookup_ms` 中位数 9.75 ms，n = 20，容器内测得）+ 回答结束后写 Redis（约 1 ms，未单独测）；相对 LLM 路径的数秒可以忽略。**没有测关闭缓存时同一批问题的延迟作为对照**（未测）。

## 5. 命中与未命中的延迟（e2e，真实 LLM）

`reports/semantic_cache/20261002T052836Z/`（`e2e.json`、`e2e_rows.jsonl`；脚本 `scripts/bench_cache_latency.py e2e --flush`）。条件：真实 DeepSeek（请求模型与响应模型都是 `deepseek-flash`）、`DATA_AS_OF=2026-09-28`、宿主机 Python 客户端 → docker 端口映射（用户态代理）→ 容器内 ai-service `POST /v1/chat/stream`、公共库范围、缓存阈值 0.80 + 守卫；10 个问题，每个依次：① 第一次 ② 原句再问 ③ 同义改写 ④ 只差一个关键要素的相近问题；n = 10 / 组；git `558db399`（dirty=true：当时只有文档与脚本未提交）。

| 组 | 命中 | 首字（中位数 / 最大） | 总耗时（中位数 / 最大） | token 合计 |
|---|---|---|---|---|
| ① 第一次（未命中） | 0 / 10 | 5409.7 / 21606.2 ms | 5776.4 / 22161.6 ms | 126458 |
| ② 原句再问 | **10 / 10** | **56.8** / 62.8 ms | **58.1** / 63.7 ms | 0 |
| ③ 同义改写 | **10 / 10**（相似度 0.832–0.980） | 54.4 / 63.4 ms | 57.5 / 64.3 ms | 0 |
| ④ 只差一个关键要素 | **0 / 10**（守卫否决，重新跑 Agent） | 6149.2 / 9663.6 ms | 6262.6 / 10495.1 ms | 120916 |

- 命中时回放的正文与第一次**逐字相同**（10 / 10）；相近问题得到的是新生成的、与原回答不同的答案（10 / 10）。
- 命中响应约 55–60 ms，其中缓存查询只占约 10 ms（`cache_lookup_ms`），其余是容器端口映射与 HTTP 开销，**这个数字不是缓存自身的下限**。样本只有 10 个问题，「最大」就是 p95/p100，不要当分布来读。
- **经 backend 的一次完整链路**（`scripts/e2e_s10.py`，gRPC，含反代 / 鉴权 / 限流检查）：第一次 15.5 s（19163 token），命中 0.16 s（0 token）。`reports/s10/20261002T053314Z_e2e/e2e_s10.json`（22 / 22 项通过；更早的一次 `…053124Z_e2e` 是 21 / 22，唯一失败项是脚本里查 MySQL 的辅助函数有缺陷，已修，保留不删）。

## 6. 复现

```bash

python -m fund_ai.eval.cache_calibration test --dev-run ../reports/cache_calibration/<dev 目录>   # 已用掉，会拒绝
python -m fund_ai.eval.cache_calibration addendum --run ../reports/cache_calibration/<目录>
# 开销与延迟（ai-service 的 venv；e2e 需要全栈 + SEMANTIC_CACHE_ENABLED=true + 真实 LLM 密钥）

ai-service/.venv/Scripts/python scripts/bench_cache_latency.py e2e --flush
ai-service/.venv/Scripts/python scripts/e2e_s10.py
```
