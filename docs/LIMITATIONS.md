# 已知局限（LIMITATIONS）

按阶段追加。每条写明影响范围和对应的 ADR。

## 第一期局限汇总（S8 收尾时按主题归并；细节和证据在下面各阶段小节，括号里是对应的小节与条号）

**评测结论能说明什么、不能说明什么**
- 端到端回答评测只有 test 124 题、每题每配置跑一次，按类型拆分后每组 2–15 题；vector 与 hybrid_rerank 在端到端得分上没有可检出的差别（CI 含 0），细小差异不能当结论（S8-7）。
- 回答准确率的口径偏保守且有已知误判：numeric 用「第一个相容数字」是下界，entity 二选一题会误判，「SQL 正确率」是端到端口径（S8-3、S8-4）；LLM 裁判与被测模型同源、可能偏宽，人工盲标只覆盖 text 类抽样（S8-2）。
- 工具选择 / 出处准确率按数据集标注的 `expected_tools` / `evidence` 衡量，持仓类题 Agent 走 SQL 也答对，仍被记为「漏调」（S8-5；S4-3）。
- 检索数字（S4）与回答数字不在同一个索引上：重建索引后 BM25 路有小幅波动，原因未验证（S8-1）。检索命中口径严，绝对水平不高（S4-1、S4-2、S4-3、S4-6）。

**Agent 与合规**
- 事实措辞错误没有自动拦截（份额张冠李戴：dev 冒烟的 003095 写成 C 类、test 里 qa-0055 把 A/C 份额数字说反），出处只保证「引用的编号存在」，不保证「数字与出处一一对应」（S5-1、S5-6，回答评测的 numeric_any_vs_first.md）。
- 输出守卫是关键词启发式，只标记不改写，会漏报；荐基拒答靠 prompt + 守卫，不是对抗性安全边界；提示注入没有系统性测试（S5-4、S6-3）。
- 延迟：首 token 中位数秒级（hybrid_rerank 7.8 s，vector 4.1 s，CPU 重排 + 单并发 + 本机进程），没有请求总超时，没有启动预热；不支持 DeepSeek 思考模式（S5-2、S5-5、S5-7、S8-8）。

**数据**
- 快照 / 披露 PDF 取自东方财富的非官方接口与转载件，冻结在 2026-09-28，不含实时数据（最新净值除外）；申购费取自招募说明书而非销售平台；数据质量有已登记的不一致（001551 销售服务费）；LOF 按场外份额收录；AkShare 若干接口缺陷靠绕行（S1-1…S1-5）。
- 只收能直接提取文字的 PDF，没有 OCR；私有库同样不支持扫描件（S6-6）。
- 最新净值的评测参考值与被测工具取自同一个上游接口（S8-6）。

**私有知识库、后端与前端**
- 私有库的检索 / 回答质量没有评测集，也没有注入测试；入库任务在内存里，重启会丢；鉴权较简（JWT 无吊销、`/internal` 只靠共享密钥）；无限流与配额（S6-1…S6-11）。
- 前端没有浏览器端 e2e 测试；令牌在 localStorage；没有公共库文件清单页；风险提示文案前端有一份拷贝（S7-1…S7-6）。
- 部署只面向单机 compose：无副本、无镜像漏洞扫描、依赖未锁哈希；首次启动要手动做数据步骤，采集流水线没有从零重跑（S7-10、S7-11）。

## 数据采集（S1）

1. **AkShare 1.18.97 取不到申购费率**：`fund_fee_em(indicator="申购费率")` 恒返回空表。原因是 AkShare 按东方财富费率页的小标题取表，但代码只认「申购费率（前端）」，页面现在的标题是「申购费率」。本项目不修改 AkShare 源码，改从招募说明书的费率表解析申购费分档（ADR-027）。因此申购费数据的时效等于最新一版招募说明书，而不是销售平台的实时展示；表格版式无法解析的份额记为缺口。
2. **AkShare 1.18.97 的人事公告接口在 0 条结果时报错**：`fund_announcement_personnel_em` 对没有公告的基金抛 `Length mismatch`，流水线把它当作空结果（ADR-027）。
3. **东方财富接口是非官方接口**：公告列表（JJGG）、净值、排行等接口没有稳定性承诺，字段可能变化；流水线固定 AkShare 版本、本地缓存原始结果，接口变化时直接报错而不是静默补值。
4. **披露 PDF 取自东方财富转载件**：证监会基金电子披露网站从本机命令行不可达（PLAN §2.1），PDF 使用 `pdf.dfcfw.com` 上由基金管理人发布的转载件，MANIFEST 记录 URL 与 sha256。
5. **LOF 按场外份额收录**：160219、161035 是 LOF，只使用场外 A/C 份额的净值和费率，不涉及场内交易价格（ADR-030）。

## 检索（S4）

以下数字都来自 test 集检索评测，n=72（79 题去掉 7 道 unanswerable），原文 `reports/retrieval/20260929T090548Z/`。

1. **绝对水平不高**：最终配置 hybrid_rerank 的 hit@5 = 0.653、nDCG@10 = 0.532。命中口径较严（要求 doc_id 相同且引文 50% 连续片段落在块里），同一条款出现在年报和招募说明书时只算其一，所以数字低于「找到能回答问题的内容」的比例（后者未另行度量）。
2. **纯 RRF 混合检索不如单独 BM25**：hybrid（RRF，k=60）nDCG@10 0.3633，bm25 0.3854，点估计低 0.022（未做配对 CI）。观察到的解释是 bge-small-zh-v1.5 在 20 只基金、文档大段雷同的语料上区分力弱（vector 单路 0.2004），等权 RRF 被它拖累；该解释未做消融验证。有效的提升来自重排（hybrid → hybrid_rerank +0.169）（ADR-039）。
3. **持仓类问题检索很弱**：holdings（11 题）hybrid_rerank nDCG@10 只有 0.126。持仓表格块的入库方式不改（ADR-039）；持仓题的主路径是 `run_fund_sql` 查 `holdings_top10` 表，文档检索只作补充。原因（持仓表碎片、表格行只有数字）是观察到的现象，未验证。
4. **实体过滤默认关闭**：dev 上关更好，test 上开 +0.022 但 95% CI [−0.010, +0.065] 含 0，按协议不据 test 改配置（ADR-038）。S5 `search_fund_documents` 的 `fund_codes` 由 Agent 显式传入，与该开关独立。
5. **重排在 CPU 上慢**：20 个候选每次约 2.7–4.6 秒，只适合离线评测；线上需要 GPU、缩小候选数或换更小的重排模型（S12–S13 评估）。
6. **样本量小**：dev 30 题、test 72 题，按 topic 拆分后每类只有 8–13 题，CI 很宽。

## Agent（S5）

数字来自 live 冒烟 `reports/agent_smoke/20260929T103710Z/`（13 题，单次运行，不是评测）。

1. **回答的正确性还没有量化**：S5 只验证协议层面的事实（用了什么工具、有没有出处、风险提示是否发出）。冒烟里我读原文时发现 1 处事实错误（tool-calc-2 把 003095 写成 C 类，003095 实际是 A 类），没有自动检查能拦住这类措辞错误；准确率、出处准确率要等 S8 的回答评测。
2. **首 token 延迟高**：冒烟 13 题中位 7.3 s（含全部工具轮和 160 字开场白扣留；只调一次工具的题 2.3–3.5 s）。文档检索在 CPU 上带重排要数秒，且服务重启后第一次检索要加载模型（约 20 s，没有做启动预热）。
3. **开场白扣留是启发式**（ADR-042）：LLM 在调用工具前常先说一句，服务端扣留每轮前 160 字来吞掉它；超过 160 字的开场白会漏给用户（`done.preamble_leaked_chars` 如实上报），最终回答最前面 160 字会晚到。值是看 13 题冒烟样本定的，换模型 / prompt 要重看。
4. **输出守卫是关键词启发式**：只标记不改写（PLAN 第一期要求），会漏报（换个说法就检测不到），也可能误报（第一次冒烟就有 1 例，已补疑问词）。拒答是否可靠要看 S8 的 advice_request 评测；冒烟只有 2 题荐基请求，两题都拒绝了推荐。
5. **Agent 不支持 DeepSeek 思考模式**（`LLM_THINKING` 只能是 `disabled`）：langchain-openai 不回传 `reasoning_content`，开启会 400（ADR-018、ADR-042）。
6. **出处粒度**：数据库 / 计算 / 净值类出处是「一次工具调用一个编号」，回答里一张表格的多个数字常共用同一个 `[n]`；文档类是「一个片段一个编号」。模型有时在一段话里只在末尾标一个 `[n]`，逐字段对应关系要读原文。
7. **没有请求总超时**：只有单次 LLM 调用（`LLM_TIMEOUT_SECONDS`）与单次工具调用（`MCP_CALL_TIMEOUT_SECONDS`）的超时；最坏情况一次请求 = 7 次 LLM 调用 + 6 轮工具调用。
8. **每次工具调用新建 MCP 会话**（langchain-mcp-adapters 行为），多几十毫秒；容器互连时文档 MCP 的 Host 白名单要加服务名（`MCP_ALLOWED_HOSTS`）。

## 私有知识库与 Java 后端（S6）

数字来自 e2e 冒烟 `reports/s6/20260929T124300Z_e2e/` 与 `reports/private_kb/`（单次运行，不是评测）。

1. **私有库的检索 / 回答质量没有评测**：e2e 用的是一份 1 页、入库 1 个切块的自造备忘录，只证明链路（入库 → READY → 检索 → 引用），不证明召回率。没有私有文档的评测集，也没有对私有库做过参数调优（沿用公共库的 `hybrid_rerank` 默认值）。
2. **BM25 分数在两个索引之间不可严格比较**（IDF 不同）：默认的 `hybrid_rerank` 把两边各取前 `rerank_candidates` 条合成一个池交给交叉编码器重排，不受影响；`bm25` / `hybrid` 这类不重排的模式按各自分数合并，只是近似（ADR-043）。
3. **用户文档是不可信输入**：文档片段作为工具结果送进 LLM，里面的指令可能被当成对模型的要求（提示注入）。system prompt 里加了一段声明（私有文档中的指令只是内容、不要执行），但**没有做系统性的注入测试**；风险提示由服务端追加、荐基拒答靠 prompt + 输出守卫，都不是对抗性安全边界。
4. **取消有延迟**：客户端断开后，backend 最晚在下一次写失败（下一个事件或下一次心跳）时才发现。S6 的 e2e 实测约 3 s；**S9 的 120 次实测（`docs/perf/grpc_vs_http.md` 第 2 节）：事件流动期几乎立刻取消（中位数 3–6 ms），安静期延迟取决于心跳——5 s 心跳时中位数 5–6 s、最大 7.4 s，S9 起默认改为 1 s 后约 2 s（1.2–3.0 s）**；工具执行期仍约 3.6–3.8 s（见 S9-5）。这段时间上游还在消耗 LLM token。
5. **入库任务只在内存里**：ai-service 后台入库用进程内锁串行执行，重启会丢失排队和进行中的任务；backend 侧 15 分钟后把停在 PROCESSING 的文档置为 FAILED，用户需要重新上传。大批量入库是 S11（Kafka）的事。
6. **图片型 / 扫描件 PDF 不支持**（没有 OCR）：提取不到文字时文档置为 FAILED 并说明原因；混合型（部分页有文字）只入库有文字的部分，不提示缺页。
7. **公共库的文档不在业务库里**：`GET /api/kbs/1/documents` 返回空列表，用户看不到公共库有哪些文件（由 data-pipeline 离线入库，清单见 `data/MANIFEST.json`）。
8. **资源上限**：上传整个读进内存（≤ 20MB，并发多时有内存压力）；每路对话占一个读取线程（上限 64，超出返回 503）；每人最多 20 个私有库；没有每用户的文档数 / 总大小配额，也没有限流（S10）。
9. **鉴权较简**：JWT 无吊销 / 刷新（12 小时有效）；用户名大小写不敏感（MySQL 排序规则）；登录没有防暴力破解；`/internal/**` 只靠共享密钥，没有 IP 限制或 TLS。
10. **多 worker 部署必须固定 `KB_SCOPE_SECRET`**：未配置时 ai-service 启动时随机生成，多个 worker 各有一个，Agent 签的令牌可能落到另一个 worker 上验不过（工具报「检索范围无效」）。当前单 worker 不受影响。
11. **私有库的文件名会出现在回答与出处里**，用户上传的敏感文件名会被展示给自己（不会给别人）；删除文档 / 知识库会联动删除向量和关键词索引，但**不会**清理 LLM 供应商侧已经收到过的对话内容。

## 前端与容器化（S7）

1. **前端没有浏览器端自动化测试**：只有 vitest 单测（SSE 解析、事件状态、Markdown 与角标渲染、出处摘要、风险提示与范围选择组件）；整页交互靠人工在浏览器里验收（截图见 PROGRESS S7），没有 Playwright 之类的 e2e。
2. **风险提示文案在前端有一份拷贝**（`frontend/src/lib/constants.ts`），用于「回答结束后仍没有服务端 disclaimer」时的兜底和页面底部的常驻提示。服务端改文案时要同步改这里，目前没有测试把两处绑在一起（ADR-045）。
3. **出处只能看片段，不能看原文件**：披露 PDF 不入仓库、不对外提供，出处展示 `snippet`（≤400 字）、页码和章节；私有库文件的原文件也不提供下载。
4. **公共库文件清单页仍没有**：公共库页只显示说明文字（与 S6-7 同一件事）。
5. **流式渲染每来一个 token 就重新解析整段 Markdown**：回答几千字以内没有观察到卡顿，但**没有专门测过长回答的渲染开销**（未测）。
6. **令牌存在 localStorage**：XSS 时可被读走。缓解措施是回答里的 HTML 一律经 DOMPurify 清洗（禁 `script`、`img`、事件属性等，有单测），但没有 CSP 头。令牌 12 小时过期后，任意请求 401 会清登录态并跳回登录页，没有刷新令牌。
7. **「停止」按钮是客户端断开**：backend 经心跳最晚延迟一个心跳间隔（约 5 s）才取消上游 LLM 调用（S6 局限 4）；期间已生成的部分以 `CANCELLED` 保存，刷新后仍能看到。
8. **检索范围记在浏览器里**（localStorage）：换浏览器要重新勾选；被勾选的范围只是「申请」，backend 逐个校验（ADR-043）。
9. **`npm audit` 有 2 条 moderate**（vitest 3 依赖的 `@vitest/mocker`，仅开发期）；不进构建产物，未升级（ADR-045）。
10. **镜像与部署**：ai-service 镜像含 CPU 版 torch，体积大；首次构建要下载依赖（本机实测各镜像构建耗时见 PROGRESS S7）；镜像构建跳过测试（测试在 CI）；没有做镜像漏洞扫描、没有固定 pip / maven 依赖的哈希；compose 只面向单机（无副本、无滚动升级）。ai-service 单 worker。
11. **首次启动要手动做数据步骤**：下载模型、导入快照、入库（README）；采集步骤（联网抓取 PDF 与结构化数据）本次全栈验收**没有从零重跑**，只验证了「快照导入 + 入库」。

## 回答评测方法（S8）

1. **同一份数据重建索引后，BM25 模式的结果会变**：容器内 `down -v` 重新入库（切块数、分布与之前完全一致，13812 块）后，用同一配置重跑 test 检索评测，vector / vector_rerank 与 S4 run 9 逐题逐名次一致，但走 Elasticsearch BM25 的模式变了：nDCG@10 bm25 0.3854 → 0.3910（+0.0056）、hybrid 0.3633 → 0.3640（+0.0007）、hybrid_rerank 0.5321 → 0.5300（−0.0021），bm25 的 top10 有序列表在 60/72 题上不同，hybrid_rerank 有 7 题指标不同（qa-0004 由 1.0 变为 0，qa-0042 由 0 变为 1.0）。同一索引上连跑两次一致，说明差异来自索引状态而非随机性；**原因未验证**（可能与重建后段结构不同影响 BM25 统计有关，旧索引已删，无法对照）。所以整体指标在 ±0.006 内波动、逐题可以翻转；S4 的检索数字与 S8 的回答数字不在同一个索引上，不能逐题对照。证据：`docs/tuning_log.md` run 11、12，`reports/retrieval/20260929T164941Z/`。
2. **裁判与被测模型是同一个模型（deepseek-flash）**：text 类的 0/1/2 分和 refusal 类的判断由 deepseek-flash 给出，自己判自己，**可能有自我偏好，给分偏宽**。最初的设计是用 deepseek-v4-pro 作裁判（与被测模型不同源），用户在费用关卡后决定改用同一个模型（ADR-046）。人工盲标的一致率与 kappa 就是用来检验这一点的：**36 行（26 道不同的题）上精确一致 34/36 = 94.4%，Cohen kappa 0.478**，两处分歧方向相同（裁判给 2、人给 1，裁判偏宽），且都是 no_tool 类通用概念题；只有 2 行分歧、人工只有 3 个非满分，所以既不能说「裁判没有偏宽」，也无法量化偏宽程度，kappa 在标签这么不均衡时不稳定（结果见 README 与 `reports/answer_eval/20260929T171529Z/blind_agreement.json`）。盲标只覆盖抽到的 text 类回答，refusal 类的裁判判断没有人工核对；36 行不是 36 道独立的题（同一题在两个配置下的回答可能都被抽到）。
3. **规则判分是启发式**（`fund_ai/eval/scoring.py`）：numeric 主口径取「回答里第一个相容数字」，回答先罗列别的相关数字再给答案时会被判错，反过来先给出别的数字却碰巧等于标准答案时会被判对；`any` 口径只作参考。entity / list 靠「标准答案文字出现在回答里」，回答用了简称或别名（池内基金名以 `universe.yaml` 为准）会被判错；二选一 / 比较题靠「标准答案先于其他候选出现」。这些口径在看到 test 结果前写定，dev 小样后修订过三处（ADR-046）。判分器已用评测集的参考回答做自洽检查，但**没有**对 Agent 的真实回答做过人工全量复核。
4. **「SQL 结果正确率」是端到端口径**：tool_sql 类题最终回答判对的比例，加上 run_fund_sql 至少成功一次的比例；**没有**单独重跑 Agent 写的 SQL 去和 gold_sql 的结果比对，所以不能区分「SQL 对、回答措辞错」与「SQL 错」。
5. **工具选择与出处准确率按数据集的 `expected_tools` / `evidence` 衡量**：fund_qa 里持仓类题标注的必需工具是 `search_fund_documents`，而 Agent 常改走数据库（`holdings_top10`）并答对——在这两个指标上会被算作「漏调工具 / 出处未命中」，但答案本身是对的（S4 局限 3 也指出持仓题的主路径本来就是 SQL）。这是数据集标注与系统实际路径的差别，不是评测口径的疏漏，报告里对这类题另有说明。
6. **最新净值题的参考值来自同一个上游接口**：评测脚本用自己的代码（不经被测的 MCP 工具）请求东方财富净值接口，但上游是同一个非官方接口；两次请求之间接口若恰好刷新，会出现假阴性。该接口不可用时被测工具回退到快照并标 `stale`，会判为错。样本只有 3 题。
7. **样本小、单次运行**：test 共 124 题（fund_qa 79 + agent_tasks 45），按 topic / 类型拆分后每组只有 2–15 题；每个配置每题只跑一次（没有重复取平均），Agent 的 temperature 为 0 但 LLM 服务端仍可能有非确定性，所以细小的差异（一两题）不能解读为配置差异；配对 bootstrap 的 CI 反映的是题目抽样，不含 LLM 运行间的随机性。
8. **延迟是单并发、CPU 上的数字**：并发 1 顺序执行，重排在 CPU 上，服务是本机进程（不是容器），DeepSeek 接口延迟随时间波动；不同时间段（费用高峰 / 非高峰）跑的两个配置之间，延迟差异不能全部归因于检索配置。
9. **费用是估算与实测的对照，不是精确账单**：`done.usage` 不区分缓存命中，实测费用按「输入全部未命中」计价，是上界；失败 run 的 token 用量服务端没有上报，未计入。

## gRPC 改造（S9）

数字来自 `docs/perf/grpc_vs_http.md`（单机、单次运行集合、n 与条件见该文件，**不是压测基线**——压测是 S12）。

1. **传输对比是预实验，不是结论**：假 ai-service（无 LLM、无检索）+ 本机回环 + 单并发，量的只是传输 / 序列化 / 客户端解析的开销；真实对话里延迟由 LLM（秒级）和检索（百毫秒～秒级）决定，传输差异在其中可以忽略。结果里 gRPC 在**突发**事件流（300 个 token 事件背靠背发出）下总耗时反而比 HTTP 高，原因是 grpc.aio 每条消息一次异步发送，而 SSE 的小写入会被合并；token 之间有真实间隔（模拟 LLM 输出速度）时两者没有可见差别。
2. **gRPC 端口没有鉴权、没有 TLS**（与 HTTP 接口一致，信任内网）：compose 只把它绑定到宿主机回环；任何能连上 50051 的进程都能提问、入库、删除文档。生产化需要 mTLS 或至少共享密钥拦截器。
3. **Java 侧 `Retrieve` 没有客户端方法**（backend 没有调用点）；Python 侧实现并有单测，需要时给 `AiServiceClient` 加方法即可。入库完成的回调仍是 ai-service → backend 的 **HTTP** 回调，没有改成 gRPC。
4. **gRPC 路径与 HTTP 路径的已知差别**：数组字段总是输出（见 API.md）；backend 在 gRPC 模式下没有「每路对话占一个读取线程（上限 64，超出 503）」的并发上限（回调在线程池里串行执行、线程只在处理事件时占用），所以过载保护要靠 S10 的限流，不再靠线程池拒绝。
5. **「客户端断开 → 上游取消」的延迟由 backend 发现断开的时刻决定，与上游用 HTTP 还是 gRPC 无关**：两种传输下 backend 决定取消到 ai-service 的 Agent 被取消只差几毫秒（120 次：差值中位数 2 ms，最大 113 ms，`docs/perf/grpc_vs_http.md` 第 2 节），但 backend 只有往浏览器写失败时才知道浏览器断了（Tomcat 的限制）。心跳从 5 s 改成 1 s 后安静期延迟约缩短 3 倍；**工具执行期（断开发生在 `tool_start` 之后）仍约 3.6–3.8 s，检测时刻与 `tool_end` 事件的写入重合，1 s 心跳没有更早发现，原因没有查清**（怀疑与 docker 用户态端口代理处理半关闭的方式有关，没有在直连环境下复验）。根治需要不依赖写失败的断开检测，未做。
6. **`BackendIntegrationTest`（Testcontainers）本机无法运行**（本机没有 Docker 环境给 Testcontainers 用），只在 CI 验证；gRPC 相关的 Java 测试（in-process 服务端）不依赖 Docker，本机已全部运行。

## 语义缓存与限流（S10）

数字来自 `docs/perf/semantic_cache.md` 与 `reports/cache_calibration/`（单机、条件与 n 见各文件，**不是压测基线**——压测是 S12）。

1. **校准集是模板生成 + 手写，不是真实用户的提问**（`eval/datasets/CACHE_PAIRS.md`）：措辞由执行者写，没有人工审核标签，基金池只有 20 只。同义改写对的难度很可能被低估，recall 83.7% 是「在这套句子上」的数字；真实说法更杂，命中率会更低，误命中也可能出现校准集里没有的形态。
2. **关键要素守卫是启发式词典，不是证明**：词典里没有的区分维度它看不见。test 上 3 / 132 的误命中全部来自这类（「股票」vs「港股通标的股票」× 2、「仓位变化」vs「市场展望」× 1）。词典是在知道整套数据集设计的情况下写的，所以另报只含 dev 问题里出现过的概念的 B_dev（test 结果与全量词典相同，说明这 3 次误命中不是靠「test 专用词条」才漏掉的，但也说明词典扩充没有帮到它们）。**扩充词典之后 test 就不再是样本外数据，需要新的校准集（v2）。**
3. **2.3%（0.8%–6.5%）是「缓存里恰好已经有一个只差一个要素的近邻」条件下的误命中率**：测试集里每个难负例都是这样构造的。真实流量里这种近邻出现的概率远低于 100%，所以生产误命中率更低，但**没有测过**。生产里缓存可能有很多条、取 top-3 逐个过守卫，候选多了误命中的机会也多，校准只量了「一对问题」的决策。误命中的后果是**把别的问题的答案当成这个问题的答案**（金融场景里数字可能直接是错的），所以缓存**默认关闭**。
4. **守卫偏保守，会损失 recall**：test 上相似度 ≥ 阈值但被守卫否决的同义改写有 11 / 92，原因：3 对是数据集的畸形问题（见 `CACHE_PAIRS.md` 已知缺陷）、2 对是「2025年年底」与「2025年末 / 12月31日」（我的年末规则没覆盖「年年底」）、4 对是一边写了「基金经理」另一边没写、1 对是「现在是哪位基金经理在管」与「现任基金经理」（词典没有这种说法）、1 对是一边写了「2026年」另一边没写年份（保守地不当成同一个问题）。因为是 test 上看到的缺陷，**没有改守卫**（改了就污染 test）。
5. **只缓存单轮、无历史的提问**：同一个会话里的第二个问题起，backend 会带上对话历史，按设计不走缓存（追问依赖上文）。所以产品里缓存主要服务「不同用户 / 不同会话问同一个问题」。相对时间词（「今天」「现在」「实时」）、荐基类、用过最新净值的回答也不缓存（规则与理由见 ADR-048）。
6. **缓存键里没有 `fund_data` 的内容**：只有 `DATA_AS_OF`、公共库 `MANIFEST.json` 的哈希、私有库版本、模型 / 提示词指纹、嵌入模型。同一个 `DATA_AS_OF` 下直接改库里的数据不会让缓存失效（TTL 24 小时兜底）。私有库版本 = READY 文档数 + 最近更新时间，极端情况下（同一毫秒删一个再加一个）可能不变。
7. **没有单飞**：同一个未命中问题并发到达会各自跑一遍 Agent，各自写缓存。**回放没有节奏**：`token` 事件一口气发完（不模拟逐字输出的速度），前端会瞬间显示全文。回放里的 `tool_end.duration_ms` 是原始那次的耗时，不是这次的。
8. **命中路径含一次 CPU 嵌入**（实测见 `docs/perf/semantic_cache.md`）；嵌入模型在 ai-service 进程里推理，并发高时和检索 / 重排抢 CPU，S12 压测要单独看。向量索引是 `FLAT`（暴力检索），库里条目到万级以上要换 `HNSW`；Redis `maxmemory` 是 192 MB、`noeviction`，缓存条目带 24 小时 TTL 但没有容量上限，写满后写入会失败（只记 warn、不影响对话）。
9. **限流与配额的默认值是经验值**（用户容量 10 / 0.5 个每秒，全局 100 / 10 个每秒，每日 200 次、50 万 token），没有按压测结果校准（S12）。令牌桶只保护对话接口，注册、登录、上传没有限流。
10. **配额的 token 是软上限且不含被取消的对话**：token 数要等 `done` 才知道，开始前只检查已用量；客户端中途断开的对话没有 `done`，已经消耗的 LLM token 不计。**Redis 不可用时放行**（保护措施不应成为故障点），那段时间没有限流 / 配额。
11. **配额回写是定时的**（默认 30 秒）：backend 在两次回写之间被杀，Redis 里的计数还在（`appendonly yes`），不会丢；Redis 数据也丢了的话，最近一个周期的计数丢失（当天配额可能被多用一点）。`usage_daily` 只存每日汇总，没有逐次明细。
12. **`BackendIntegrationTest` 仍然只能在 CI 跑；S10 新增的 Redis / MySQL 测试默认用 Testcontainers（CI）**，本机没有可供 Testcontainers 连接的 Docker，是靠 `FRA_TEST_REDIS` / `FRA_TEST_MYSQL` 指向一次性容器跑的（见 `testsupport/TestRedis.java`）；这些测试在 CI 里的 Testcontainers 路径是第一次运行，以 CI 结果为准。
